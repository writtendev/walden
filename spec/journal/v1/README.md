# Walden Journal Specification: Format v1

> **Status:** Published Specification (v1)  
> **Milestone:** M1 · Journal format v1  
> **Ruling:** Ruling 2 of 5 (Stream Model and Key Layout)

## 1. Overview and Coordinate Model

The walden journal is an append-only, content-addressed, tamper-evident log stored in S3-compatible object storage.

The journal format defines **`(stream-id, seq)`** as its primary coordinate:
- **`stream-id`**: A string identifying the log stream.
- **`seq`**: A 64-bit unsigned integer (`0` to `18,446,744,073,709,551,615`), zero-indexed, strictly monotonic with no gaps.

Every repository is modeled as an independent stream. The server instance's own internal state — including the server signing identity, key rotations, and token table mutations — is recorded in a reserved **meta stream** (`_meta`).

```
                              (stream-id, seq)
                                      │
               ┌──────────────────────┴──────────────────────┐
               ▼                                             ▼
       Repository Stream                                Meta Stream
    stream-id = "<repo-id>"                         stream-id = "_meta"
 ┌─────────────────────────────┐               ┌─────────────────────────────┐
 │ seq 0: First push ref tx    │               │ seq 0: Genesis (public key) │
 │ seq 1: Second push ref tx   │               │ seq 1: Token create (rwc:*) │
 │ seq 2: Force-push ref tx    │               │ seq 2: Token revoke (...)   │
 └─────────────────────────────┘               └─────────────────────────────┘
```

## 2. Stream Model and Partitioning

### 2.1 Repository Streams
- Each repository corresponds to exactly one stream.
- The stream ID is the caller-chosen repository identifier (e.g., `my-repo`, `blog`, `r_8f3a2b1c`).
- Stream IDs MUST consist only of URL-safe ASCII characters (`[a-zA-Z0-9._-]`), MUST NOT contain path traversal sequences (`..`), MUST NOT start or end with `/`, and MUST NOT exceed 255 bytes.
- A repository stream begins at `seq = 0` upon the first accepted push.

### 2.2 The Meta Stream (`_meta`)
- The reserved stream ID `_meta` is dedicated to instance configuration and authentication metadata.
- `seq = 0`: **Genesis record** — declares the server's signing identity (public key) minted on first boot (Ruling 1).
- `seq >= 1`: Token store mutations (token creation, revocation) and signing key rotation records.
- The `_meta` stream maintains its own independent sequence counter and compare-and-swap lease.

### 2.3 Per-Stream Fencing
- Fencing is strictly isolated per stream:
  - A writer appending to a repository stream conditions on that repository stream's sequence number.
  - A writer appending to the meta stream conditions on the meta stream's sequence number.
  - A conditional-append conflict on repository stream $A$ transitions stream $A$ to `fenced` on that instance, but has **no effect** on repository stream $B$ or on the `_meta` stream.

## 3. Object Storage Key Space Layout

All keys in the journal reside under a common base prefix `v1/streams/<stream-id>/` (optionally prepended with an operator-configured bucket prefix).

```
v1/streams/<stream-id>/
├── tx/
│   ├── 00000000000000000000.json
│   ├── 00000000000000000001.json
│   └── 00000000000000000002.json
├── segments/
│   ├── <sha256-hex-1>.pack
│   └── <sha256-hex-2>.pack
├── snapshots/
│   └── <sha256-hex-snapshot>.pack
└── marker.json
```

### 3.1 Ref and Meta Transactions (`tx/`)
- **Key Pattern:** `v1/streams/<stream-id>/tx/<seq>.json`
- **Sequence Formatting:** `<seq>` is encoded as a 20-digit zero-padded decimal unsigned 64-bit integer (`%020d`, range `00000000000000000000` through `18446744073709551615`).
- **Content:** Immutable JSON record describing ref updates or metadata mutations, signed by the server signing identity.

### 3.2 Pack Segments (`segments/`)
- **Key Pattern:** `v1/streams/<stream-id>/segments/<sha256>.pack`
- **Hash Formatting:** `<sha256>` is the 64-character lowercase hexadecimal SHA-256 digest of the exact received git packfile bytes.
- **Content:** The raw, uncompressed/verbatim git packfile payload.
- **Idempotence:** Writing identical pack bytes produces the identical key. An upload to an existing segment key is idempotent and MUST succeed as a no-op.

### 3.3 Snapshots (`snapshots/`)
- **Key Pattern:** `v1/streams/<stream-id>/snapshots/<sha256>.pack`
- **Hash Formatting:** 64-character lowercase hexadecimal SHA-256 digest of the consolidated packfile generated by background compaction.
- **Content:** Consolidated git packfile containing all objects reachable up to the compacted sequence.

### 3.4 Replay Marker (`marker.json`)
- **Key Pattern:** `v1/streams/<stream-id>/marker.json`
- **Content:** JSON document indicating the highest consolidated sequence number and the corresponding snapshot object.
- **Publish Order:** The compactor MUST write and verify the snapshot packfile *before* writing or updating `marker.json`.

## 4. Lexicographical Ordering Guarantees

Object storage listings (`LIST` / `ListObjectsV2`) return keys in UTF-8 binary lexicographical order. Implementations and readers MUST adhere to the following rules:

| Key Category | Key Pattern | Lexicographically Ordered by Sequence? | Reader Assumptions and Invariants |
| :--- | :--- | :---: | :--- |
| **Transaction Records** | `v1/streams/<stream-id>/tx/<seq>.json` | **YES** | Keys sort in strictly ascending numerical sequence order. A reader listing with prefix `.../tx/` and optional `start-after` receives transactions in replay order. Every sequence MUST equal `previous_seq + 1` with no gaps. |
| **Pack Segments** | `v1/streams/<stream-id>/segments/<sha256>.pack` | **NO** | Keys sort in random cryptographic hash order. A reader MUST NOT assume any chronological or sequence ordering among segments. Segments are referenced by hash inside transaction records. |
| **Compaction Snapshots** | `v1/streams/<stream-id>/snapshots/<sha256>.pack` | **NO** | Keys sort in hash order. Must be resolved exclusively via `marker.json`. |
| **Replay Marker** | `v1/streams/<stream-id>/marker.json` | **N/A** (Single key) | Direct GET. Points to the baseline snapshot and the starting sequence for incremental replay. |
| **Stream Directory** | `v1/streams/<stream-id>/` | **NO** (Alphabetical) | Stream IDs sort alphabetically by byte values (`_meta`, `app`, `blog`, `zeta`). Reader MUST NOT infer stream creation time or relationship from stream listing order. |

## 5. Fencing and Compare-and-Swap (CAS)

1. **Conditional Append:** Every write to `v1/streams/<stream-id>/tx/<seq>.json` MUST be executed as a conditional PUT requiring that the target key does not yet exist (`If-None-Match: *` or provider equivalent).
2. **Conflict as Fencing:** If the conditional PUT returns a precondition failure (HTTP 412 or equivalent), the writer has lost single-writer status to a concurrent or newer writer.
3. **Strict Invariant:** Upon receiving a precondition failure, the writer MUST transition that stream into a permanent `fenced` state for the life of the process. It is **strictly forbidden** to re-read the stream head sequence and retry the append.
4. **Per-Stream Isolation:** Fencing on stream $A$ does not affect the writer's lease on stream $B$ or on `_meta`.

---

## 6. Reader and Replay Rules

To materialize or restore a stream from the journal:

1. **Locate Marker:** Check for `v1/streams/<stream-id>/marker.json`.
   - If present: Load the referenced snapshot packfile from `v1/streams/<stream-id>/snapshots/<sha256>.pack` and initialize the repository state at `marker.sequence`.
   - If absent: Begin replay from `seq = 00000000000000000000`.
2. **Scan Transactions:** Perform a paginated `LIST` under `v1/streams/<stream-id>/tx/` with `start-after` set to the last materialized sequence.
3. **Verify Continuity:**
   - Verify that sequence numbers are strictly contiguous ($s_0, s_0+1, s_0+2, \dots$).
   - Any gap indicates journal truncation or missing objects and MUST cause materialization to abort loudly with a one-line error.
4. **Apply and Verify:** Apply ref updates in sequence order, fetching required pack segments by content hash. Superseded segments present in storage but not referenced in active replay MUST be ignored.
